### 1. Мотивация

Компания «Александрит» столкнулась с ростом нагрузки, потерей заказов, деградацией интерфейсов и негативом клиентов. Сейчас:

* Нет видимости, где теряются заказы
* MES тормозит → операторы недовольны → падает скорость производства
* Отсутствует контроль SLA для партнёрского API → растёт недовольство B2B клиентов
* Релизы часто ломают производительность, а проблемы замечаются только после жалоб

Мониторинг поможет:

| Польза бизнесу                          | Технический эффект            |
| --------------------------------------- | ----------------------------- |
| Снижение доли просроченных заказов      | Быстрый поиск узких мест      |
| Удержание B2B клиентов                  | Контроль производительности   |
| Сокращение времени инцидентов и простоя | Alerting до жалоб клиентов    |
| Рост доверия и прозрачности             | Основания для масштабирования |

**Мониторинг — это защита денег компании и её репутации.**

---

### 2. Выбор подхода к мониторингу

Система содержит разнородные компоненты, поэтому используем комбинированный подход:

| Подсистема                      | Подход                                    | Обоснование                                  |
| ------------------------------- | ----------------------------------------- | -------------------------------------------- |
| Публичные API (Shop, CRM, MES)  | **RED (Rate, Errors, Duration)**          | Критично SLA и ошибки пользователей          |
| Инфраструктура (EC2, БД)        | **USE (Utilization, Saturation, Errors)** | Контроль пропускной способности и перегрузок |
| RabbitMQ и асинхронные процессы | **Four Golden Signals**                   | Требуется отслеживать задержки и очереди     |

Так мы получим полную картину: от UX → до железа и очередей.

---

### 3. Метрики для мониторинга

Ниже — только выбранные метрики + описание бизнес-ценности.

#### API (Shop, CRM, MES) — RED

| Метрика                       | Зачем                             | Ярлыки                 |
| ----------------------------- | --------------------------------- | ---------------------- |
| **RPS per API**               | Определяем рост нагрузки, SLA B2B | api_name, status_class |
| **Latency p95 / p99**         | Контроль пользовательского опыта  | endpoint               |
| **Количество HTTP 500 / 400** | Видим сломанные релизы заранее    | api_name, method       |
| **Active sessions**           | Признак нехватки ресурсов         | api_name               |

---

#### RabbitMQ — Golden Signals

| Метрика                         | Зачем                             | Ярлыки        |
| ------------------------------- | --------------------------------- | ------------- |
| **Messages in-flight**          | Обнаружение «зависших» заказов    | queue_name    |
| **DLQ message count**           | Прямая метрика потерянных заказов | queue_name    |
| **Message processing duration** | Видим деградацию MES              | consumer_name |

---

#### MES & Базы данных — USE

| Метрика                        | Зачем                     | Ярлыки      |
| ------------------------------ | ------------------------- | ----------- |
| **CPU% / Memory% для MES API** | Защититься от тормозов UI | instance_id |
| **DB connections count**       | Ловим connection leaks    | db_role     |
| **DB size**                    | Не допустить остановку БД | -           |
| **S3 size for 3D files**       | Прогноз затрат            | bucket      |

Дополнительно:
**Количество заказов по статусам** — для операционного мониторинга
label: order_status

### 4. Предлагаемое расширение списка метрик

| Метрика                                      | Обоснование                            |
| -------------------------------------------- | -------------------------------------- |
| **Order state stuck time** (время в статусе) | Определить SLA нарушителей             |
| **Pricing calculation time**                 | Контроль ключевого узкого места        |
| **API throttling hits**                      | Контроль превышений на партнёрском API |
| **RabbitMQ retry count**                     | Предиктивное предупреждение проблем    |

### 5. План действий (драфт технического задания)

| Этап | Что делаем                                                                | Результат                          |
| ---- | ------------------------------------------------------------------------- | ---------------------------------- |
| 1    | Развернуть **Prometheus + Alertmanager + Grafana**                        | Централизованный сбор метрик       |
| 2    | Настроить экспортёры: Node Exporter, RabbitMQ Exporter, Postgres Exporter | Метрики с сервисов и БД            |
| 3    | Добавить RED-метрики в Shop/CRM/MES API (OpenTelemetry/Prometheus SDK)    | Контроль SLA                       |
| 4    | Дашборды для SLA и состояния заказов                                      | Видимость для бизнеса              |
| 5    | Настроить алерты на критичные показатели                                  | Быстрые реакции без жалоб клиентов |
| 6    | Автоматическая проверка при релизах                                       | Раннее обнаружение деградаций      |

Дополнительно:

* APM (Jaeger) для трассировки задержек между сервисами

### 6. Пороговые значения насыщенности и реакции (опционально)

| Показатель                            | Порог        | Действие                        |
| ------------------------------------- | ------------ | ------------------------------- |
| Latency API p99 > 2 сек               | 5 мин подряд | Авто-скейлинг + тикет DevOps    |
| DLQ > 0                               | Немедленно   | PagerDuty on-call               |
| CPU API > 80%                         | >10 мин      | Добавить инстансы               |
| DB connections > 85% лимита           | >5 мин       | Увеличить пул / анализ запросов |
| Pricing calculation time > 15 мин p95 | Сразу        | Расследование + масштабирование |

**Главная цель алертов — обнаружить проблему быстрее, чем клиент заметит.**
