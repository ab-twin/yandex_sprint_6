# Задание 1

**Планирование: анализ, идентификация проблем и поиск решений**

### Анализ архитектуры и проблем

#### Текущие и потенциальные проблемы

**Оркестрация заказов**

* Нет единого источника правды по статусам заказа → возникают: задержки, расхождения статусов, потерянные сообщения.
* Логика распределена между CRM, MES и Shop → высокая сложность и нежелательные зависимости.

**Интеграции и коммуникации**

* Использование RabbitMQ без гарантированной доставки и без DLQ → теряются сообщения.
* Нет трекинга обработки событий → сложно расследовать, где «сломался» заказ.
* MES API перегружен функциями (и цена, и статусы, и список, и назначения операторов).

**Производительность MES**

* UI MES тормозит при большом количестве заказов даже с пагинацией → вероятное отсутствие оптимизации SQL/индексов.
* Список заказов строится медленно из-за больших джойнов + отсутствие выборок только активных заказов.

**Производительность расчёта цены**

* Расчёт 2–30 минут блокирует пользовательский поток → большой риск таймаутов и повторов.
* Нет асинхронной модели запроса и кэширования результатов.

**Нагрузки и масштабирование**

* Все сервисы по одному инстансу → SPOF и отсутствие горизонтального масштабирования.
* Базы имеют по одному мастеру → риск отказа, конкуренция запросов растёт.

**API для партнёров**

* Резкий рост нагрузки → система не выдерживает поток внешних заказов.
* Жалобы B2B → компании теряют контракты → прямые финансовые последствия.

**Процессы DevOps**

* Release/prod — ручные деплои → медленные релизы, частые откаты.
* QA вручную гоняет регрессию → огромные задержки спринтов.

### Инициативы для устранения проблем

| №   | Инициатива                                   | Описание                                                            | Ожидаемый результат                                    |
| --- | -------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------ |
| I1  | Введение **Order Orchestrator**              | Выделить централизованный сервис управления жизненным циклом заказа | Сокращение потерь статусов, прогнозируемость процессов |
| I2  | Введение **DLQ + retry policy** в RabbitMQ   | Контроль и доставка всех сообщений                                  | Исключение потерь заказов                              |
| I3  | Асинхронный расчёт стоимости + нотификации   | MES считает цену в фоне, Shop опрашивает статус                     | Снижение таймаутов, повышение UX                       |
| I4  | Масштабирование сервисов                     | Запуск нескольких инстансов + авто-скейлинг                         | Рост нагрузки без деградации                           |
| I5  | Оптимизация MES UI + отдельные выборки       | Быстрая загрузка активных заказов, индексы                          | Увеличение скорости работы операторов                  |
| I6  | Monitoring & Alerting (Grafana + Prometheus) | Видимость SLA по процессам                                          | Быстрое реагирование на проблемы                       |
| I7  | Feature toggles & Canary deploy              | Уменьшение рисков релизов                                           | Быстрые, безопасные релизы                             |
| I8  | Автоматизация тестирования                   | UI + API автотесты, тест пайплайн                                   | Сокращение задержек релизов                            |
| I9  | Архитектурное разделение MES API             | Микросервисы: pricing, assignment, order view                       | Масштабируемость, снижение зависимости                 |
| I10 | Caching pricing results                      | Хранить результаты расчётов для повторных запросов                  | Снижение нагрузки на MES                               |
| I11 | SLA для внешнего API                         | Queue throttling + rate-limit                                       | Стабильность B2B потока                                |

### Приоритизация инициатив и обоснование

#### Наивысший приоритет (Q1–Q2)

1. **I6 - Monitoring & Alerting & Logging**

   * Поможет понять, где на самом деле находятся критические проблемы
   * Выявить ключевые места для планирования задач

2. **I1 — Order Orchestrator**

    * Ряд критических проблем с заказами именно из-за потери/рассинхронизации статусов
    * Улучшает UX и восстанавливает доверие B2B клиентов

3. **I2 — Надёжная доставка сообщений**

    * Устраняет потерю заказов
    * Снижает нагрузку на поддержку и MES

4. **I4 — Масштабирование сервисов + база** (* дополнительно)

    * Нагрузка растёт ежемесячно
    * Неприменение → паралич системы в ближайшие месяцы

#### Второй уровень приоритета (параллельно)

* **I3** Асинхронный расчёт стоимости — моментальный эффект на NPS
* **I5** Быстродействие MES для операторов → прямая прибыль
* **I8** Автотесты → устранение релизных задержек

### Целевая архитектура через полгода

* Настроенный Monitoring & Alerting & logging
* Оркестратор заказов (state machine) → единое управление статусами
* MES разделён на сервисы **Pricing**, **Execution**, **Assignment**
* Горизонтальное масштабирование всех критичных сервисов
* Сообщения гарантированно доставляются, полностью мониторятся
* Асинхронная модель интеграции с B2B API
* MES UI быстрый, с оптимизированной БД и выборками
* CI/CD ускорен: меньше ручного труда, больше автоматизации

**Главный эффект:**
* заказы не теряются
* сроки исполнения соблюдаются
* восстановлен доверенный B2B поток
* бизнес растёт устойчиво
