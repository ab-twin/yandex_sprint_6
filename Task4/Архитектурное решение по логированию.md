# Архитектурное решение по логированию

## 1. Мотивация

Сейчас инциденты и нестандартные ситуации разбираются «по рассказам клиентов» и операторов. Это приводит к тому, что:

* поддержка и разработчики тратят часы и дни на восстановление картины события;
* часть инцидентов вообще не удаётся воспроизвести;
* бизнес не может объективно оценить масштаб проблем (сколько заказов сломалось, где именно они застревают).

### Что даст централизованное логирование

**Для бизнеса:**

1. **Сокращение времени расследования инцидентов (MTTR)**
   → быстрее восстанавливаем работу, меньше просроченных заказов, меньше возвратов и штрафов от B2B-партнёров.

2. **Прозрачность работы системы**
   → можно ответить на вопросы «что произошло с заказом N» не по памяти сотрудников, а по точной хронологии.

3. **Раннее обнаружение проблем и атак**
   → по логам видно всплески неуспешных заказов/ошибок, попытки DDoS или злоупотреблений партнёрским API.

**Для техники:**

1. **Снижение нагрузки на поддержку и разработчиков**
   → меньше ручных запросов в БД, grep по логам на серверах, меньше «пожаров».

2. **Более качественный трейсинг и мониторинг**
   → логи дополняют метрики и трассировки: в них можно увидеть бизнес-контекст, параметры запросов, а не только синтетические показатели.

3. **Основа для автоматизации алертинга и анализа аномалий**
   → по логам можно строить алерты (например, всплеск HTTP 500, аномальный рост заказов из одного API-ключа).

### Метрики, на которые повлияет логирование

* **MTTD / MTTR** (время обнаружения и устранения инцидентов) — за счёт возможности быстро найти корень проблемы по логам.
* **Доля просроченных заказов** — если вовремя замечать «зависания» по логам и устранять причины.
* **Количество обращений в поддержку по техническим проблемам** — снижение за счёт более предсказуемого поведения и быстрого анализа.
* **Надёжность интеграций с партнёрами (B2B SLA)** — логирование ошибок и таймаутов на уровне API снижает долю «потерянных заказов».

## 2. Что и где логируем

### 2.1. Системы, из которых нужно собирать логи

На C4-диаграмме логирование должно быть настроено для следующих контейнеров:

1. **Shop API (онлайн-магазин)**

    * создание и изменение заказов (INITIATED, FILE_UPLOADED, SUBMITTED);
    * взаимодействие с MES API и RabbitMQ (публикация сообщений).

2. **CRM API**

    * MANUFACTURING_APPROVED, CLOSED;
    * создание заказов от внешних API (B2B);
    * обработка событий из RabbitMQ.

3. **MES API + MES backend**

    * расчёт стоимости (PRICE_CALCULATED);
    * назначения операторов, статусы MANUFACTURING_STARTED / COMPLETED / PACKAGING / SHIPPED;
    * работа с 3D-хранилищем.

4. **Message Queue (RabbitMQ)**

    * ошибки доставки сообщений;
    * попадание сообщений в DLQ;
    * повторные обработки.

5. **Фронтенды (Internet Shop, CRM, MES)**

    * ошибки на клиенте (JS-ошибки, невозможность обратиться к API) — в минимальном объёме, с проксированием в backend.

6. **Инфраструктура**

    * HTTP-логи запросов к API (для аналитики и расследований).

### 2.2. Список ключевых логов уровня INFO

Ниже — то, что **обязательно логируем на уровне INFO** (без чувствительных данных).

#### Shop API

1. **Создание заказа (INITIATED/SUBMITTED)**

    * `event=order_created`
    * `order_id`, `customer_id/anonymous_id`, `channel` (site / api), `created_at`.

2. **Загрузка/сохранение 3D-модели (FILE_UPLOADED)**

    * `event=model_uploaded`
    * `order_id`, `file_id`, `file_size`, `polygons_count` (если есть), `storage_key`.

3. **Отправка события в RabbitMQ о новом заказе**

    * `event=order_submitted_published`
    * `order_id`, `routing_key`, `message_id`.

4. **Получение ответа о цене от MES**

    * `event=price_received`
    * `order_id`, `price`, `pricing_duration_ms`.

#### CRM API

5. **Подтверждение производства (MANUFACTURING_APPROVED)**

    * `event=manufacturing_approved`
    * `order_id`, `crm_user_id`, `approval_source` (auto/manual).

6. **Закрытие заказа (CLOSED)**

    * `event=order_closed`
    * `order_id`, `close_reason` (delivered / cancelled / returned / manual_fix).

7. **Создание заказа из внешнего API (B2B)**

    * `event=order_created_b2b`
    * `order_id`, `partner_id`, `external_order_id`.

#### MES API / MES backend

8. **Запуск расчёта стоимости (PRICE_CALCULATED start)**

    * `event=price_calculation_started`
    * `order_id`, `model_id`, `estimated_complexity`.

9. **Завершение расчёта стоимости**

    * `event=price_calculated`
    * `order_id`, `price`, `duration_ms`, `success=true/false`.

10. **Назначение оператора на заказ**

    * `event=order_assigned`
    * `order_id`, `operator_id`, `assignment_strategy`.

11. **Обновление статуса производства (MANUFACTURING_*)**

    * `event=order_status_changed_mes`
    * `order_id`, `status_from`, `status_to`, `operator_id`.

12. **Операции с 3D-хранилищем**

    * `event=3d_storage_access`
    * `order_id`, `operation` (read/write), `result` (success/fail).

#### RabbitMQ / интеграции

13. **Сообщение отправлено в очередь**

    * `event=message_published`
    * `queue`, `message_type`, `message_id`, `order_id` (если есть).

14. **Сообщение прочитано и обработано**

    * `event=message_consumed`
    * `queue`, `consumer`, `message_id`, `order_id`, `processing_duration_ms`.

15. **Сообщение попало в DLQ**

    * `event=message_dead_letter`
    * `queue`, `reason`, `message_id`, `order_id`.

#### Фронтенды

16. **Ключевые пользовательские действия**

    * `event=ui_order_submitted` (интернет-магазин);
    * `event=ui_operator_take_order` (MES);
    * атрибуты: `user_id`, `order_id`, `client_version`.

### 2.3. Другие уровни логирования и когда их использовать

* **DEBUG**

    * Подробные технические детали: SQL-запросы, содержимое сообщений, шаги алгоритмов.
    * Включается **точечно и временно** (по флагу/конфигу) при расследовании сложных багов на dev/release, в проде — только для отдельных сервисов и на короткое время.

* **INFO**

    * Основной поток бизнес-событий и ключевых технических фактов.
    * Используется для восстановления жизненного цикла заказа.

* **WARN**

    * Нештатные, но не критичные ситуации:

        * повторные попытки отправки сообщений,
        * таймауты обращения к внешним системам,
        * превышение SLA, но с успешным восстановлением.

* **ERROR**

    * Ошибка операции, из-за которой бизнес-операция не выполнена:

        * не удалось провести заказ в новый статус,
        * не удалось записать результат расчёта цены,
        * не удалось прочитать 3D-файл.

* **FATAL / CRITICAL**

    * Ошибки, при которых сервис не может продолжать работу:

        * недоступна БД,
        * не поднимается основной HTTP-сервер.
    * Такие ошибки должны быть связаны с алертами.

## 3. Приоритеты: что логировать и трассировать в первую очередь

Одновременно покрыть логами и трейсингом всё нельзя, поэтому выделяем приоритеты:

### 1-й приоритет (критичный для бизнеса)

1. **MES (API + backend)**

    * Здесь происходят расчёт цены и производство — ключ к SLA и жалобам клиентов.
    * Здесь же сложная логика, которая приводит к «зависанию» заказов.

2. **RabbitMQ и обработчики событий**

    * Потеря/двойная обработка сообщений → потерянные или задвоенные заказы.
    * Логирование и трейсинг тут дают возможность видеть судьбу каждого сообщения.

3. **Shop API (входная точка заказов)**

    * Все B2C заказы начинаются здесь.
    * Ошибки на этом уровне напрямую отражаются на конверсии.

### 2-й приоритет

4. **CRM API**

    * Подтверждение производства, закрытие заказов, работа B2B.
    * Важно для полного пути заказа, но можно подключать после MES/Shop/RabbitMQ.

5. **Фронтенды MES и CRM**

    * Для разведки проблем UX (оператор «видит не то» или «не видит заказ»).

Трейсинг и логирование в первую очередь — для **MES + Shop API + RabbitMQ**, чтобы закрыть корневые бизнес-проблемы с потерей и зависанием заказов.

## 4. Предлагаемое решение

### 4.1. Технологический стек

Для логирования используем классический стек:

* Fluent Bit / Filebeat — сбор логов с контейнеров;
* Elasticsearch — хранилище логов (time-series / индексы);
* Kibana — UI для поиска и анализа логов;
* Интеграция с уже выбранной системой мониторинга (Prometheus/Grafana) и трейсинга (OpenTelemetry + Jaeger).

Причины:

* хорошо интегрируется с Kubernetes и cloud-инфраструктурой;
* поддерживает структурированные JSON-логи;
* удобен для построения дашбордов, фильтрации по полям `order_id`, `service`, `level` и т. д.

### 4.3. Политика безопасности логов

1. **Минимизация чувствительных данных**

* В логах **запрещено** хранить: ФИО, телефоны, e-mail, адреса, платёжные данные.
* В логах оставляем только идентификаторы (`customer_id`, `order_id`, `partner_id`).
* Для ошибок валидации выводим общие сообщения без раскрытия персональных данных.

2. **Контроль доступа**

* Log UI доступен только по корпоративной учётной записи (SSO / LDAP).
* Роли доступа:

    * **Support** — чтение логов по заказам и API-ошибкам;
    * **Developers** — чтение + технические детали, возможность сохранять saved searches;
    * **Admins/DevOps** — полный доступ, управление индексами и retention.

3. **Сетевые ограничения**

* Хранилище логов и UI доступны только из приватной сети (VPC) и по VPN.
* Прямого доступа из интернета нет.

4. **Шифрование и аудит**

* Логи шифруются на уровне дисков (encryption at rest).
* Доступ к логам логируется, чтобы в случае утечки видеть, кто просматривал данные.

### 4.4. Политика хранения и структура индексов

**Индексы:**

* Разделение по типам логов:

    * `logs-shop-*` — Shop API;
    * `logs-crm-*` — CRM API;
    * `logs-mes-*` — MES;
    * `logs-mq-*` — RabbitMQ и инфраструктура.
* Опционально — разделение по окружениям:

    * `logs-shop-prod-*`, `logs-shop-dev-*` и т. п.

**Retention:**

* Продакшн:

    * 30 дней для подробных логов;
    * 90 дней для агрегированных/ключевых событий (order lifecycle).
* Dev/release:

    * 7–14 дней.

**Размер:**

* Ограниченный размер индекса (например, 20–50 ГБ) с автоматическим rollover:

    * при достижении лимита создаётся новый индекс;
    * старые индексы по истечении срока retention автоматически удаляются.

## 5. От сбора логов к системе анализа

### 5.1. Алертинг

Логи становятся базой для:

* алертов по ERROR/FATAL событий:

    * всплеск `level=ERROR` в Shop API или MES;
    * превышение порога по `event=message_dead_letter` в RabbitMQ.
* алертов по бизнес-событиям:

    * слишком много неуспешных заказов `event=order_created` + последующие ошибки;
    * отсутствие логов `price_calculated` для значимого числа заказов.

Реализация:

* либо через встроенные возможности Kibana Alerting;
* либо через экспорт логовых метрик в Prometheus и алерты в Alertmanager.

### 5.2. Поиск аномалий

Примеры:

* В обычном режиме создаётся 3–5 заказов/секунду, но внезапно стало 10 000:

    * возможная DDoS-атака, ошибка партнёрского интегратора, баг в клиентском коде.
* Резкий рост `message_dead_letter` или `order_status_changed` с ошибкой.

Подход:

* Настроить дашборды с агрегацией количества событий по типу и времени;
* Для ключевых сценариев (создание заказа, расчёт цены, изменение статуса) — задать пороговые значения;
* Для B2B API клиентов — отдельные дашборды по `partner_id`, чтобы видеть аномальное поведение.
