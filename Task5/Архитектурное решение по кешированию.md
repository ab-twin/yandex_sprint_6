# Архитектурное решение по кешированию

## 1. Мотивация

### Текущие проблемы

1. **Медленная работа MES для операторов**

* Страница списка заказов долго загружается, даже после внедрения пагинации и фильтров по статусам.
* Операторы конкурируют за новые заказы («кто первый возьмёт — тот и заработает»), поэтому задержка загрузки страницы напрямую влияет на их доход и удовлетворённость.

2. **Низкая скорость обработки заказов в целом**

* Клиенты (и B2C, и через B2B API) жалуются на медленное исполнение заказов.
* Частично это связано с тем, что MES API и БД перегружены чтением списков заказов и состояниями, замедляя другие операции (в т. ч. расчёт и обновление статусов).

3. **Рост нагрузки**

* Нагрузка растёт линейно: каждый месяц +100 заказов.
* После открытия B2B API поток заказов сильно увеличился.
* MES и его БД стали «бутылочным горлышком» и для операторов, и для расчёта/обработки.

### Зачем нужно кеширование

Кеширование в контуре MES нужно, чтобы:

* **ускорить чтение часто запрашиваемых данных** (списки заказов, детальная информация по заказу);
* **снизить нагрузку на БД MES**, чтобы высвободить ресурсы для критичных операций (расчёт цены, обновление статусов);
* **улучшить UX операторов**: быстрая загрузка списков заказов и их актуальных статусов;
* обеспечить более предсказуемое время ответа и лучшее соблюдение SLA для B2B-партнёров.

### Что именно имеет смысл кешировать

1. **Списки заказов для операторов в MES**

* Запросы вида:

    * `GET /orders?status=NEW` — новые заказы;
    * `GET /orders?status=IN_PROGRESS&operatorId=...` — заказы в работе;
    * `GET /orders?status=COMPLETED` — завершённые.
* Это самые частые запросы со стороны MES UI, повторяющиеся много раз при рефрешах страницы, автоподгрузке и т. д.

2. **Карточка заказа (детальная информация)**

* `GET /orders/{orderId}` — просматривается многократно до завершения заказа.
* Данные меняются относительно редко (несколько раз за жизненный цикл).

3. **Сводные данные для дашбордов операторов**

* Число новых заказов по статусам, привязка к оператору, агрегированные показатели.
* Могут кешироваться как отдельные агрегаты.

**Не будем кешировать**:

* операции записи (создание/изменение заказов) как таковые;
* тяжёлый расчёт цены **мы решаем первично асинхронностью и оптимизацией**, а не кешированием, т. к. большинство моделей уникальны.

## 2. Предлагаемое решение

### 2.1. Тип кеширования: клиентское vs серверное

**Клиентское кеширование (браузер MES):**

* Работает для статических ресурсов (JS/CSS/иконки) и можно настроить через HTTP-заголовки (`Cache-Control`, `ETag`).
* Частично помогает скорости загрузки фронтенда, но **не решает основную проблему**: медленные ответы MES API и БД.

**Серверное кеширование (MES API):**

* Позволяет разгрузить БД MES и сократить время ответа API.
* Дает централизованный контроль над сроком жизни данных и инвалидацией.
* Работает и для операторов, и для B2B API, и для других внутренних сервисов.

### 2.2. Выбор паттерна кеширования

Для серверного кеша рассмотрим три классических паттерна:

* **Cache-Aside** (lazy loading, «кеш рядом»);
* **Write-Through**;
* **Refresh-Ahead**.

#### Основной паттерн: Cache-Aside

**Идея:**

* При чтении:

    1. MES API сначала пытается прочитать данные из кеша (Redis).
    2. Если кеш-промах (cache miss) — читает из БД, возвращает ответ клиенту и параллельно записывает результат в кеш с TTL.
* При записи/изменении статуса:

    * Сначала пишем в БД,
    * потом **инвалидируем (удаляем)** соответствующие записи в кеш (по ключу/ключам).

**Почему Cache-Aside:**

* Простой в реализации и понятный команде;
* Хорошо подходит для сценариев, где **больше чтений, чем записей** (именно так устроены списки заказов);
* Позволяет гибко управлять TTL и инвалидацией, без сложного согласования между кешем и БД;
* При отказе кеша система продолжает работать (чуть медленнее, но корректно).

#### Почему не Write-Through

* При write-through любое изменение статуса заказа должно сразу **сначала** записаться в кеш, а затем проксироваться в БД.
* Для MES это усложнит логику, потребует строгой синхронизации кеша и БД и не даст существенных преимуществ, т.к. число записей относительно невелико (по сравнению с чтениями списков).

#### Почему не Refresh-Ahead

* Refresh-Ahead эффективен, когда легко предсказать, какие данные будут нужны в ближайшее время, и можно их заранее обновить.
* В MES заказы создаются и переходят по статусам достаточно хаотично; предсказать, какие списки (фильтры, операторы, статусы) будут востребованы через N минут, сложно.
* Реализация станет существенно сложнее, а выигрыш относительно Cache-Aside будет небольшой.

Поэтому **основной паттерн** — **Cache-Aside** с проработанной стратегией инвалидации.

### 2.3. Техническая реализация

**Компоненты:**

* **MES API (C#)** — добавляет слой кеширования при чтении списков и карточек заказов.
* **Кеш-хранилище** — Redis (Managed Redis в Yandex Cloud) или аналогичный in-memory distributed cache.
* **MES DB (PostgreSQL)** — остаётся источником истины.

**Ключи кеша:**

1. Список заказов для оператора:

    * `orders:list:status={status}:operator={id}:page={n}:size={k}`
2. Список новых заказов (без оператора):

    * `orders:list:status=NEW:page={n}:size={k}`
3. Карточка заказа:

    * `orders:item:{orderId}`

**TTL (примерные значения):**

* Списки заказов: 10–30 секунд (данные активно обновляются, нужен компромисс между свежестью и производительностью).
* Карточка заказа: 30–60 секунд.

## 4. Стратегия инвалидации кеша

Для MES целесообразно комбинировать **временную** инвалидацию (TTL) и **инвалидацию по ключу** при изменении заказа.

### 4.1. Временная (TTL)

**Что:** у каждого ключа есть срок жизни (например, 30 секунд).

**Плюсы:**

* проста в реализации;
* автоматически очищает старые записи, не требуя явной инвалидации;
* защищает от ситуаций, когда какую-то ветку инвалидации забыли реализовать.

**Минусы:**

* в окне `0–TTL` секунд данные могут быть немного устаревшими;
* не обеспечивает мгновенного отражения изменений при критичных событиях (например, когда оператор взял новый заказ, а другой оператор всё ещё видит его как «свободный»).

### 4.2. Инвалидация по ключу (программная)

**Что:** при изменении статуса или создании заказа MES API **явно удаляет** или обновляет записи в кеш по соответствующим ключам.

**Плюсы:**

* изменение статуса быстро отражается в UI;
* позволяет уменьшить TTL, не опасаясь большого числа промахов.

**Минусы:**

* требует аккуратного дизайна ключей (чтобы понимать, какие ключи нужно удалить);
* требует дисциплины разработчиков: при добавлении новых фильтров нужно обновлять логику инвалидации.

### 4.3. Сравнение стратегий (для списков заказов)

| Стратегия                  | Лучше подходит, потому что…                                               | Особенности / ограничения                                                                                              |
| -------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Только TTL                 | Простая реализация, минимум логики в коде                                 | Возможны «фантомные» свободные заказы ещё несколько секунд; не подходит, когда важна мгновенная конкуренция операторов |
| Только по ключу            | Обеспечивает максимально актуальные данные                                | Сложная логика инвалидации, легко ошибиться и забыть удалить нужный ключ                                               |
| TTL + инвалидация по ключу | Компромисс: быстро отражаем важные изменения и чистим «хвосты» по времени | Рекомендуемый вариант: TTL небольшой (10–30 сек) + явная инвалидация при статусных изменениях                          |

👉 **Предлагаемое решение:**
использовать **комбинированную стратегию**:

* Списки и карточки заказов кешируются с **коротким TTL (10–30 секунд)**;
* При изменении статуса или назначении оператора осуществляется **явная инвалидация ключей**:

    * карточка конкретного заказа (`orders:item:{id}`);
    * списки, в которых этот заказ мог участвовать (по статусу и оператору, через префикс/теги).

## 5. Сравнение вариантов решений по кешированию (дополнительно)

### Вариант 1. Простое Cache-Aside + Redis (предложенное решение)

* Кешируются списки заказов и карточки;
* Инвалидация: TTL + по ключу;
* Кэш — отдельный Redis-кластер.

### Вариант 2. Материализованные представления / read-model (условный CQRS)

* Вместо кеша строится отдельная «читающая» БД (например, денормализованная таблица или Elastic/OpenSearch), куда реплицируются изменения заказов;
* MES UI читает данные из read-model, а не из основной БД.

|                       | Решение 1: Redis Cache-Aside                    | Решение 2: Read-model / materialized views            |
| --------------------- | ----------------------------------------------- | ----------------------------------------------------- |
| Описание              | In-memory кеш перед текущей БД MES              | Отдельное хранилище для чтения, обновляемое событиями |
| Сложность реализации  | Низкая/средняя                                  | Высокая: нужны события, репликация, поддержка схемы   |
| Время до первых выгод | Быстро: 1–2 спринта на MVP                      | Дольше: 3+ спринтов, серьёзный рефакторинг            |
| Гибкость запросов     | Ограничена структурой кешируемых данных         | Можно оптимизировать под отчёты и сложные запросы     |
| Риски                 | Ошибки инвалидации → временно устаревшие данные | Несоответствие между write-моделью и read-моделью     |

**Вывод:**
Для горизонта ближайших 6–12 месяцев и текущих задач «ускорить MES и снизить жалобы» **достаточно и рациональнее внедрить Решение 1 (Redis Cache-Aside)**.
Read-model можно рассматривать как эволюционный шаг позже, когда будет необходима серьёзная аналитика и отчётность поверх заказов.

---

## 6. Заключение

Предложенное архитектурное решение по кешированию в MES:

* адресует ключевую проблему **медленной работы списка заказов для операторов**;
* снижает нагрузку на БД MES и освобождает ресурсы для других операций (расчёт цены, обновление статусов);
* сохраняет **корректность данных** за счёт комбинированной стратегии инвалидации (TTL + по ключу);
* относительно просто реализуется текущей командой без серьёзных архитектурных перестроек.

Это решение хорошо сочетается с уже спроектированными мониторингом и трейсингом:
по логам, метрикам и трассам можно будет отследить, как кеш влияет на производительность и SLA, и при необходимости скорректировать TTL и объём кешируемых данных.
